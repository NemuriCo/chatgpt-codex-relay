# Codex App Server bridge

Phase 3 connects BlueRelay to the local Codex App Server over its stdio JSON-RPC transport. The implementation was checked against the locally installed codex-cli 0.148.0-alpha.9 schema generated by the local executable; generated schema files are intentionally not committed.

## Thread persistence and Desktop visibility boundary

The installed CLI schema describes `thread/start` as a persistent thread API by default. Its returned thread metadata includes the exact thread id, normalized `cwd`, `ephemeral`, `source`, and optional rollout `path`; `thread/read`, `thread/list`, `thread/resume`, and `thread/unarchive` are separate official lifecycle APIs. BlueRelay stores the exact id returned by `thread/start`, resumes that same id after an App Server process restart, and never creates an ephemeral fork for normal work.

BlueRelay sends the normalized project directory as `cwd`. If the selected directory is inside a Git worktree or repository, the nearest recognized `.git` root is used. The request intentionally omits the optional analytics-only `threadSource` field: `bluerelay` was a custom value with no verified Desktop meaning, while pretending to be `cli` or `vscode` would misrepresent the client. Approval and sandbox settings remain explicit and unchanged.

The official App Server documentation describes App Server as an integration surface for rich clients and documents `thread/list` source filters. Its default interactive filter is `cli` and `vscode`; `appServer` is a distinct source kind. It does not document that a third-party App Server client can make an arbitrary thread appear in the ChatGPT Desktop app's default thread list, nor does it document an official “open this Desktop thread” command. BlueRelay therefore exposes the Codex thread id and pairing diagnostics, but does not claim Desktop synchronization, auto-open a private Desktop route, or modify Codex SQLite/JSONL storage. Desktop visibility still requires a real Desktop/App Server integration test after the relevant Codex Desktop release is installed.

When `thread/resume` reports an archived thread, BlueRelay preserves the saved thread id, returns `codex_thread_archived`, and moves the Workstream to NeedsAttention. The user can retry the original thread or explicitly start a new Codex session; an archived session is never silently replaced or unarchived.

## Runtime behavior

- The Codex process is lazy: BlueRelay does not start it at application startup.
- BlueRelay discovers an explicitly configured executable, a real codex executable on PATH, and common per-user Codex installation locations. Windows Store execution aliases are ignored when they cannot be launched as child processes.
- The process is started without a shell or administrator elevation as: codex app-server --listen stdio://.
- The protocol client uses one JSON object per line, correlates request ids, serializes writes, handles notifications and server requests, and bounds a single message at 16 MiB.
- initialize is sent once per process, followed by the initialized notification. Each Workstream has its own Codex thread. A later task resumes the saved thread id instead of sharing a thread between Workstreams.
- turn/start sends one text UserInput containing the optional user note and the complete task.md payload. Progress is derived from typed protocol events such as item start/completion, agent-message deltas, command execution, and file changes; raw prompt/result bodies are not written to diagnostics.
- A normal turn stores the final agent message in result.md and moves the Workstream to ReadyForChatGPT. Process exit, protocol failure, or a missing result preserves the task and moves the Workstream to an actionable error state.
- Cancellation uses turn/interrupt; it does not kill the Codex process. The UI exposes a separate reset-thread action that clears only the Workstream's saved thread mapping.

## Explicit session pairing

Each Workstream keeps a durable pairing for both sides of the relay:

- ChatGPT: browser installation id, tab id, conversation id, current URL, and page title.
- Codex: the saved Codex thread id.

The browser endpoint is runtime state, while the Workstream fields are the durable identity. A ChatGPT SPA navigation that reports a different conversation marks the binding as mismatched and pauses capture and result delivery. The extension must explicitly rebind the current conversation; a normal bind request cannot silently replace an existing pairing. A stale disconnected tab may be replaced by another tab for the same conversation.

Codex thread attachment is tracked per app-server process generation. The first turn in a generation starts or resumes the saved thread; later turns reuse the attached thread without another `thread/resume`. A new process generation resumes the saved thread once. If the App Server reports that another process owns the active writer, BlueRelay keeps the current task and thread, moves the Workstream to NeedsAttention, and offers retrying the original session or starting a new Codex session. Starting a new session clears only the Codex binding; project, task, ChatGPT pairing, browser endpoint, and user note remain intact.

Routing diagnostics contain only Workstream and shortened endpoint/thread identities plus the routing decision. Prompt and result bodies are never included.

## Approval boundary

The bridge surfaces the current App Server request methods:

- item/commandExecution/requestApproval
- item/fileChange/requestApproval
- item/tool/requestUserInput
- item/permissions/requestApproval

BlueRelay presents a user decision before answering command, file-change, and permission requests. It never auto-approves a command or file change. The browser bridge and ChatGPT DOM capture remain separate from this process/protocol layer.

## Payload storage

state.json keeps short notes and payload metadata only. New task and result bodies are stored below:

%LocalAppData%/BlueRelay/relay/<workstream-guid>/<task-guid>/task.md

and:

%LocalAppData%/BlueRelay/relay/<workstream-guid>/<task-guid>/result.md

Each metadata record contains the relative path, UTF-8 byte length, and SHA-256. Older Prompt and Result fields remain readable; on the next save, payload-backed bodies are not duplicated into state.json.

## Smoke test

The test CodexAppServerSmokeTests.AppServerSmokeCanRunWhenExplicitlyEnabled is gated so normal CI and local test runs do not start Codex. It starts a real persisted App Server thread and turn, so it does write Codex's own session storage even though its prompt forbids project-file changes. Run it only when that side effect is explicitly acceptable:

~~~powershell
$env:BLUERELAY_RUN_CODEX_SMOKE = "1"
$env:BLUERELAY_CODEX_PATH = "C:\Path\to\codex.exe"
dotnet test .\BlueRelay.sln --filter FullyQualifiedName~CodexAppServerSmokeTests
~~~

The prompt asks Codex to read the first line of README.md and explicitly forbids creating, modifying, or deleting project files. A real logged-in Codex environment is required; an offline or unauthenticated App Server may not complete the turn.
